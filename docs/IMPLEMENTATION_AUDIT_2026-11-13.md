## 3. Доступы: что сохраняется

Проверены 15 обёрток, id/роль и чтение индекса. Старые пароли не менялись. «Временные» в прежних документах — обозначение пилота, не запрограммированный срок.

Индивидуальные обёртки выдают читателям общий код данных. Ключ публикации находится в отдельном объекте admin под его паролем; читательские объекты его не содержат.

Полный отзыв меняет epoch/ключ и перешифровывает текущие данные; для сохранения остальных паролей утилите нужен локальный реестр. Удаление id из нового manifest не уничтожает старую обёртку в Git. Локальный резерв паролей не равен готовому восстановлению с любого устройства.

Следствие: добавление из UI переиспользует существующую схему; безопасная смена/отзыв без локального реестра и реальные права редактора требуют отдельного проекта. Новые записи, смена ролей и ротация при этом аудите не запускались.

## 4. Проверенная процедура замены ключа публикаций

1. После отдельного решения владельца выпустить fine-grained ключ: только FRchat-data, Contents: Read and write, согласованный срок.
2. Войти прежним admin, открыть #/setup. Ввести ключ только в поле владельца; не в чат, URL или код.
3. OwnerSetup создаёт writer с новым ключом. savePublishingToken зашифровывает обновлённый объект admin прежним accessKey и сохраняет одним commit без force. Объекты читателей, ключ данных и индекс не должны меняться.
4. Проверить подтверждение подключения, повторный вход admin и неизменность читательских объектов/индекса. Успешная запись настройки проверяет разрешение записи; тестовый пост не нужен без отдельного поручения.
5. После проверки вывести старый ключ из использования, зафиксировать новый срок в закрытом реестре. Пользовательские пароли не перевыдавать.

Формат и ограничения сверены с [официальной документацией GitHub](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/managing-your-personal-access-tokens). Текущий аудит выполнял только GET и чтение срока; замены или тестовой публикации не было.

## 6. Соседние проекты

«7 дней» переиспользуется переходом и текущим JSON-адаптером. Его сценарии и прогресс не присваиваются FRchat. FrDomianReview — источник отбора документов, не автоматический импорт 657 файлов. pending в локальном manifest не доказывает отсутствие решений в отдельном хранилище.

EventFlow и прочие инструменты — кандидаты после проверки адреса/аудитории. README не является единственным доказательством состояния: описание локальности EventFlow и элементы сохранения в коде требуют сверки при подключении. Соседние проекты не изменялись.

## 7. Проверки и границы доказательств

На текущем коде прошли 43 unit tests, TypeScript, build, проверка контейнеров/IV публичного резерва и privacy scan сборки. Новый полный браузерный прогон на текущую дату не выполнялся; исторический CI не выдаётся за проверку реальных телефонов сейчас.

Главные пробелы: пустая база документов, общий origin, срок ключа публикации, ограниченный резерв, ручной жизненный цикл доступа, перенос одного сеанса, отсутствие общего прогресса/наблюдения/фоновых уведомлений. Они выделены в отдельные этапы.

Рабочие ключи, доступы, manifest, посты и сервис не менялись. Локальный build записывает только игнорируемый dist. Изменения этого шага ограничены документацией.
